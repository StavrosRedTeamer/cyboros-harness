A finding is only a finding if code can prove it.

Most AI pentest agents are built to find things. This one is built to refuse to report what it cannot prove, and to carry the lesson of one engagement into the next.

The bottleneck is not generation. It is proof.

Hand a model the advisory text and it can exploit a one-day. Point it at a real target with no description to lean on and the number collapses. This project lives in the distance between those two numbers.

  1. 87%

    of one-day vulnerabilities exploited by GPT-4 when handed the advisory text, while every other model tested scored 0%.

    Fan et al. 2024
  2. ≤13%

    resolved by the strongest agent framework on real web targets with no description to lean on.

    Zhu et al., CVE-Bench, ICML 2025
  3. ~0

    where our own runs sit on hard HackTheBox boxes. This is our own unreleased observation, not a published result, and we label it that way everywhere we repeat it.

    Unpublished, ours. Drawn hollow because it is not a citation.

So this harness moves the policy out of the prompt and into the runtime.

The agent is not the policy. The runtime is.

Every other agent in this space handles authorization with a sentence in its README and then gives the model a shell. Here the guards are separate programs that run below the model, and they fail closed.

The guard chain, in the order it runs

  1. scope-guard.js

    Nothing runs against a host absent from scope.json. Empty scope blocks everything. There is no flag to disable it.

  2. DNS-rebinding guard

    An in-scope hostname that resolves to a private, loopback or link-local address is refused unless that subnet is in allowed_ips.

  3. Rate limit and pacing

    Enforced in-process, not suggested to the model.

  4. Tiered confirmation

    A destructive or high-impact action needs a consent token. A confirm-tier action cannot start without an explicit operator grant.

The agent can decide to attack. It cannot decide whether it is allowed to.

The principle is short enough to state in a code review: a refusal by the model is a bug, because the guard already made that decision.

Severity can never exceed evidence.

record-finding.js enforces a verification ladder and rejects incoherent records instead of warning about them. The more a finding has proven, the hotter it is allowed to run.

Verification level and the severity ceiling it allows
verify_levelWhat it meansSeverity ceiling
suspectedplausible, not reproducedLow
triggeredcondition triggered, not exploitedMedium
exploitedfull exploit chain demonstratedHigh
proven_impactreal impact proven: data read, ATO, RCECritical

Proof is re-run, not described

Declare proven_impact without a valid oracle and the finding is refused. Any finding that claims reality (status: verified, or exploited / proven_impact) must carry an oracle: a machine-re-executed proof the harness runs itself, N/N times, live. 

{
  "verify": {
    "method": "GET", "url": "https://HOST/api/x", "as": "user_a",
    "expect": { "status": 200, "body_contains": "unique-marker" }
  }
}
  • Beyond status and body_contains, body_similarity_to catches the same-length IDOR a substring check misses.
  • Every finding gets an independent re-verification pass by a separate verifier agent.
  • gen-poc.js writes a parameterized Python reproducer (exit 0 means reproduced), so a human can re-run it without trusting the harness.
  • Stage gates close the loop: coverage matrix complete, no pending findings, at least one verified. Otherwise no report is produced at all.
  • Findings also leave as SARIF 2.1.0, consumed unmodified by GitHub code scanning and DefectDojo. The evidence ceiling travels with each result in properties.cyboros.

Built to run on someone else’s network.

Zero dependencies
No lockfile, no transitive supply chain, nothing to audit but the 53k lines in the repository. CI fails the build if that ever stops being true. On a client network, npm install does nothing.
Runs air-gapped
local/ drives the same deterministic engine against a local model. No API key, no data leaving the engagement laptop.
114 tests, hermetic and parallel
Offline and loopback only, no network. Shared engine state lives in a fixture, so two runs cannot influence each other. npm test is the gate.
Evidence memory that compounds
memory/ keeps sanitized technique-to-outcome lessons across engagements. The sanitizer refuses to store in-scope hosts, emails, tokens or credentials.

Node 22 or newer. No install. No network.

Clone it and run the tests first. Everything after that is gated by a file you write yourself.

bash 
git clone https://github.com/CSI-entitymorton/cyboros-harness.git
cd cyboros-harness
npm test                 # 114 tests, no install, no network

node tools/scope-guard.js check https://target.example   # exit 0 = authorized
node tools/cyboros.js recon target.example
node tools/cyboros.js scan target.example
node tools/cyboros.js status

Then write your authorization

scope.json is the written authorization. Until you fill it in, the harness refuses every target. 

{
  "allowed_hosts": ["target.example"],
  "allowed_ips": ["10.0.0.0/8"],
  "max_requests_per_second": 2
}

Authorized testing only.

Your own systems, a signed engagement scope, in-scope bug bounty targets, or a lab. scope.json names which hosts may be tested. It does not pre-authorize destructive actions; those still need explicit confirmation in the session.

One honest caveat, also stated in SECURITY.md

The guards run in-process and are not a sandbox. Tools reached through MCP bypass them, unless you mount the server through the proxy: 

node tools/mcp-guard-proxy.js -- npx -y chrome-devtools-mcp@latest --headless --isolated

The proxy puts scope-guard and ssrf-guard in series with the server. It judges every tools/call, refuses out-of-scope or rebinding targets before the request leaves the machine, and appends every decision to reports/tmp/mcp-guard.jsonl. Mount a third-party server raw and you are outside the guard, and responsible for it yourself.
